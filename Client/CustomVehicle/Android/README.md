# Android client adapter

This directory provides a JNI bridge for an Android multiplayer client that
already has a supported way to observe incoming SA-MP/open.mp RPCs and enqueue
outgoing RPCs. It is not a standalone multiplayer client, APK, game patch, or
RenderWare model loader.

## Contents

- `java/org/openmp/customvehicle/NativeBridge.java`: Java API used by an Android
  host application.
- `src/jni_bridge.cpp`: JNI implementation backed by the portable C ABI,
  session state machine, and checksum-verified file cache.
- `libcustom_vehicle_android.so`: generated by the shared CMake project when
  configured with the Android NDK.

## Build the native library

Set `ANDROID_NDK_HOME` to an installed Android NDK directory, then configure
one ABI at a time:

```sh
cmake -S Client/CustomVehicle/Shared -B build/custom-vehicle-android-arm64 \
  -DCMAKE_TOOLCHAIN_FILE="$ANDROID_NDK_HOME/build/cmake/android.toolchain.cmake" \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-24 \
  -DBUILD_TESTING=OFF \
  -DCMAKE_BUILD_TYPE=Release

cmake --build build/custom-vehicle-android-arm64 --config Release
```

The output is `libcustom_vehicle_android.so`. Repeat with `armeabi-v7a`,
`x86`, or `x86_64` for the other NDK ABIs. CI cross-compiles all four ABIs.

Copy the Java source into the host application's source set under the matching
package `org.openmp.customvehicle`, and package the generated native library
for the selected ABI using the application's normal Android build configuration.

## Host integration contract

The host constructs `NativeBridge` with:

- A `Callbacks.sendRpc` implementation that queues an outgoing RPC on the
  multiplayer client's network thread.
- A `Callbacks.beginDownload` implementation that copies the URL and metadata,
  then performs HTTP and file I/O on a worker thread.
- An app-private cache directory.

The host forwards incoming RPC IDs and exact payload bytes to
`handleServerRpc`. A return value of 1 means consume the RPC, 0 means forward
it to the original client, and -1 means invalid input. For completed downloads,
the host passes the bytes to `completeAsset`; JNI stores the verified file in
the native cache before the adapter sends RPC 184.

The downloader must call `retryActiveAsset` after its own timeout/backoff
policy. Before `close()`, the host must stop and join every worker that could
call `completeAsset`. Do not call back into `NativeBridge` synchronously from
`sendRpc` or `beginDownload`: both are invoked while adapter state is locked.
The JNI boundary limits one RPC payload to 1 MiB and one completed asset to
512 MiB because the current Java callback contract passes the full asset as a
`byte[]`. Larger assets need a streaming-file completion API rather than a
larger Java array.

The cache path is deterministic:
`dff-<8 lowercase hex CRC32>.dff` or
`txd-<8 lowercase hex CRC32>.txd`. After `completeAsset()` returns true,
call `hasAsset(type, checksum, expectedSize)` to re-read and verify the file
from disk. Only then should the host pass `assetPath(type, checksum)` to its
model loader.

## What this does not provide

The Android client must still implement all of the following:

1. A verified incoming/outgoing RakNet RPC hook for the exact multiplayer
   client and version.
2. Correct game-thread scheduling for asset registration and model lookup.
3. A RenderWare/GTA SA model backend that registers DFF/TXD files, streams the
   model, and releases resources safely.
4. Vehicle model-info lookup and vehicle construction for that specific game
   executable/engine.
5. Connection lifecycle, cancellation, and native resource cleanup.

The NDK build proves only that the bridge compiles for an ABI. It does not prove
that an Android multiplayer client exposes the RPC hook or native model APIs
needed to render a custom vehicle. No offsets or native layouts are guessed.
